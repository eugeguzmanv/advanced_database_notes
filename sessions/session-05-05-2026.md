# Session – 2026-05-12

## Topics covered
*   **ORM (Object-Relational Mapping):** A bridge between the OOP logic and relational databases. It abstracts raw SQL, letting us map DB tables to classes and rows to instantiated objects, keeping database interactions strictly within the application's native codebase.
*   **ORM DB Migrations:** Essentially version control for the database schema. Instead of executing manual `ALTER TABLE` DDL scripts, we define our data models declaratively in code. The migration engine then generates and applies the exact SQL updates required to keep the actual DB schema in sync with the current backend architecture.
*   **Alembic:** The standard migration framework for SQLAlchemy. It tracks model mutations, autogenerates migration scripts, and ensures safe, reproducible schema upgrades across environments.
*   **ORM Relationships:** Enforcing relational integrity at the application level:
    *   One-to-Many
    *   Many-to-One
    *   Foreign Key constraints
    *   Cascading deletes (handling orphaned records cleanly)

## What I understood
*   Alembic is basically Git for the database layer. It serializes schema states into migration scripts, giving us the ability to deterministically upgrade or rollback the DB state between versions.
*   Using an ORM drastically cuts down boilerplate SQL. Manipulating Python objects natively is much more efficient than parsing raw query strings for standard CRUD operations.
*   Declaring relationships at the model level (e.g., linking users to tasks) abstracts the complexity of SQL joins and enforces a logical, object-oriented data structure.
*   Migrations are critical for deployment and CI/CD pipelines. They guarantee that the schema in local development perfectly matches production, preventing runtime crashes due to structural inconsistencies.
