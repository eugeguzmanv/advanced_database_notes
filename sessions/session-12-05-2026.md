# Session – 2026-05-12
## Topics covered
* **ORM (Object-Relational Mapping):** A layer that translates relational database
structures into object-oriented code. It maps database tables directly to classes and
individual rows to object instances, allowing developers to interact with the
database natively through programming structures.
* **ORM DB Migration:** Serves as a version control mechanism for the database
architecture. Rather than executing manual SQL scripts to mutate schemas, model
configurations are declared in application code. The ORM tracks these structural
shifts to generate and execute target-agnostic SQL updates synchronously.
* **Alembic:** A dedicated schema migration tool tailored for SQLAlchemy. It monitors
declarative engine models, parses changes, and generates version-controlled delta
scripts to execute upgrades or rollbacks systematically.
* **Relationships in ORM:**

* **One-to-Many / Many-to-One:** Constructs logical associations across parent-
child entities.

* **Foreign Keys:** Physical constraint markers handling database-level references.
* **Cascading Deletes:** Automates child row sanitation rules to preserve data
integrity across dependent relationships.
## What I understood
* **Versioned Databases:** Alembic functions closely to Git for database schemas by
maintaining linear tracking files, providing reliable hooks for structural upgrades,
and managing rollbacks between structural revisions.

* **Abstracted Queries:** Utilizing an ORM abstracts SQL syntax execution into high-
level object states, decoupling developers from explicit connection routing and

inline query generation.
* **Logical Structuring:** Relational mapping streamlines context traversal, smoothly
mapping real-world references like users-to-teams or tasks-to-users.
* **Environment Synchronization:** Migrations insulate individual staging tracks,
keeping local definitions identical to active target database setups across multiple
runtime branches.
## What is still confusing
* **Redundancy of Declarative Initialization:** Clarifying the distinct operational
boundaries between initial schema bootstrap states (`Base.metadata.create_all()`) and
historical migration increments can be confusing. Initial generation scripts work
effectively during prototyping, but lack the structural rollback support and safe
incremental adjustments needed for running live deployments without experiencing data
drops.
