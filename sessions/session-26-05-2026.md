# Session – 2026-05-26

## Topics covered
* **OLTP (Online Transaction Processing):** System design structured entirely around transactional data integrity. Optimised for handling millions of granular, low-latency writes and updates in parallel while keeping current records strictly accurate.
* **OLAP (Online Analytical Processing):** Architecture focused on read-heavy historical queries and big-picture analytics. Designed to run massive, multi-dimensional aggregations over massive datastores to back strategic forecasting.
* **Star Schema:** A dimensional data modeling strategy built for analytical efficiency. It uses a heavily normalized, central Fact table filled with numeric event metrics, bordered by simplified, descriptive Dimension tables connected via clean foreign key linkages.

## What I understood
* **Multi-Dimensional Discovery:** OLAP structures corporate information into logically organized analytical hypercubes. This setup permits immediate, interactive drill-downs and roll-ups across key intersecting variables like geography, product domains, or calendar cycles.
* **Historical Synthesis:** Analytical structures cross-reference live transaction records with deeply historical data streams to build comprehensive trends.
* **Operational Engines:** OLTP architectures act as the active storefront engine, handling instant operations like banking transfers, cart adjustments, or customer verification updates where real-time accuracy and short response windows are critical.
* **Core Application Contexts:**
  * *OLTP Architectures:* Live retail checkouts, banking portals, active ticketing management systems.
  * *OLAP Environments:* Centralized enterprise data warehouses, interactive data discovery surfaces, high-level corporate metrics dashboards.
* **Data Flow Mechanics:** `OLTP -> ETL -> OLAP`
* **Pipeline Infrastructure:** ETL (Extract, Transform, Load) governs the continuous data transformation cycle between real-time entry engines and the core analytical layer.
  * *Extract:* Querying localized active datastores via SQL commands.
  * *Transform:* Cleaning structural anomalies, unifying corrupted text encoding, and pre-computing summary metrics.
  * *Load:* Writing sanitized records into target presentation tables.
* **Structural Decoupling:** Fact tables isolate hard numeric metrics generated by business transactions (e.g., items sold, records closed). In contrast, Dimension tables provide the surrounding contextual descriptors (e.g., buyer profiles, regional hierarchies, metadata states).
* **Surrogate Key Protection:** Integrating synthetic, warehouse-controlled sequence IDs into dimensions shields analytics pipelines from upstream system volatility, ensuring stable historical lookups even if source system primary keys shift.
* **Join Optimization:** The Star Schema architecture boosts performance by directly linking surrounding context dimensions to the central fact layer, significantly shortening query execution paths.

### Star Schema Structure
The centralized fact architecture explicitly isolates event measurements, exposing clear foreign key connections to non-overlapping dimension arrays to allow high-throughput query aggregation.

## What is still confusing
* **Internal Hypercube Mechanics:** The underlying engineering that controls multi-dimensional data indexing to keep query performance exceptionally fast across massive calculation scales.
* **System Boundaries:** Drawing clear architectural cutoffs between transactional and analytical behaviors in complex corporate systems, particularly when transactional engines double as operational report targets.
* **Surrogate vs. Natural Identifiers:** Clarifying the specific integration problems that emerge if natural production system primary keys are mapped straight into dimensional storage layers without synthetic encapsulation.
* **Grain Identification Boundaries:** Establishing a reproducible design pattern to separate business events from raw descriptive attributes during initial schema mapping.
